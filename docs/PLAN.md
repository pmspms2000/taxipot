# 기말 프로젝트 계획 — 캠퍼스 택시팟 (가칭)

성균관대 축제 후 귀가 택시 동승 매칭 + N분의 1 정산 웹 서비스

---

## 1. 문제 정의 (Problem)

성균관대 축제는 율전(자과캠)과 명륜(인사캠)에서 번갈아 열린다. 축제가 끝나는 밤 시간대에는:

- 대중교통이 끊겨 학교 셔틀버스에 의존해야 하는데, 수요 대비 배차가 턱없이 부족하다.
- 결국 택시를 타야 하는데 혼자 타면 비용 부담이 크다 (명륜↔율전 약 3~4만 원대).
- 학생들은 에브리타임에 "○시에 △△ 가실 분" 글을 올려 동승자를 구하지만,
  **탑승 시간·탑승 장소·하차 장소가 모두 맞는 사람을 찾기 어렵고**, 댓글/쪽지로
  조율하는 과정이 느리고 불확실하다.
- 매칭에 성공해도 내린 뒤 택시비를 나누는 정산이 번거롭고 떼먹힘 걱정이 있다.

**핵심 문제 한 줄:** "같은 시간, 같은 방향으로 갈 사람을 빠르고 확실하게 찾고, 정산까지 깔끔하게 끝내는 방법이 없다."

## 2. 고객 / 페르소나 (Customer)

> **김성균 (21, 율전캠 소프트웨어학과 2학년)**
> - 명륜캠 축제에 친구들과 놀러 갔다가 밤 11시에 축제가 끝남.
> - 지하철 막차는 이미 놓쳤고, 셔틀버스 줄은 100m 이상.
> - 택시로 혼자 가면 3만 원 이상 — 한 달 용돈으로는 부담.
> - 에브리타임에 글을 올렸지만 30분째 댓글이 없거나, 시간대가 안 맞는 사람뿐.
> - 원하는 것: **지금 바로, 같은 방향 사람 3명을 찾아서, 각자 1/N만 내고 귀가하기.**

## 3. 시나리오 (Scenario)

### AS-IS (사용 전)
1. 축제 종료 → 셔틀 줄이 너무 김 → 택시 타기로 결정.
2. 에브리타임에 동승 구인 글 작성. 새로고침하며 댓글 대기 (10~40분).
3. 댓글 단 사람과 쪽지로 시간·장소 조율 — 중간에 잠수/조건 불일치로 무산되기도 함.
4. 겨우 만나서 탑승. 도착 후 한 명이 결제하고, 카톡으로 계좌 알려주며 송금 요청.
5. 송금 안 하는 사람 생기면 얼굴 붉힘. 총 소요: 매칭까지 30분~1시간, 스트레스 높음.

### TO-BE (사용 후)
1. 축제 종료 → 서비스 접속 → 현재 열린 팟 목록에서 **하차 장소·출발 시간이 맞는 팟**을 즉시 확인.
2. 맞는 팟이 있으면 원터치 참여, 없으면 10초 만에 팟 개설 (탑승 장소·출발 시간·하차 장소·정원).
3. 정원이 차면 알림 → 지정된 탑승 장소에서 만나 출발.
4. 도착 후 결제자가 금액 입력 → 자동으로 1/N 계산 → 각자에게 토스/카카오페이 송금 링크 발송.
5. 총 소요: 매칭 5~10분, 정산 1분. 조율 스트레스 제거.

## 4. 솔루션 (Solution) — MVP 범위

**웹 서비스** (앱 심사 불필요, 에브리타임/카톡에 링크 공유로 즉시 유입 가능)

핵심 기능 (반복 1에서 시작, 이후 반복에서 확장):
1. **팟 보드**: 탑승 장소(율전/명륜 고정 거점) + 출발 시간 + 하차 장소 + 정원으로 팟 개설/참여.
2. **필터/정렬**: 내 하차 방향·출발 시간대 기준으로 맞는 팟만 보여주기.
3. **1/N 정산 도우미**: 총액 입력 → 인당 금액 자동 계산 → 토스 송금 링크(금액 포함) 생성.
   ⚠️ 실제 자동 결제(PG 연동)는 사업자 등록이 필요해 MVP 범위 밖 —
   "송금 링크 자동 생성"으로 같은 가치를 검증하고, 발표에서 TO-BE 로드맵으로 제시.
4. (후속 반복 후보) 학교 이메일 인증으로 신뢰 확보, 정원 마감 알림, 시간대 슬롯 추천.

## 5. 가설 → 제품 → 측정 반복 계획 (KPI 포함)

수업에서 요구하는 (가설 → 제품 → 검증 → 새 가설 → 새 제품) 반복. 3회 계획.

### 반복 1 — "매칭이 진짜 문제다"
- **가설 H1**: 시간·장소가 구조화된 팟 보드가 있으면, 에브리타임 자유 글보다
  빠르게 동승자를 찾는다. (목표: 팟 개설 → 정원 마감까지 중앙값 15분 이내)
- **제품**: 팟 개설/목록/참여만 있는 최소 MVP. 로그인은 닉네임+연락 수단 수준.
- **측정(KPI)**: 팟 개설 수, 팟당 참여자 수, **매칭 성사율(정원 2명 이상 모인 팟 비율)**,
  개설→마감 소요 시간. GA4 이벤트 + Supabase 데이터로 측정.
- **검증 방법**: 지인·과 단톡방 10~20명 대상 시뮬레이션 테스트 (축제 기간이 아니어도
  "금요일 밤 귀가 상황" 시나리오로 테스트 가능).

### 반복 2 — "정산이 두 번째 걸림돌이다"
- **가설 H2**: 1/N 자동 계산 + 송금 링크를 제공하면 팟 완료율(실제 탑승·정산까지
  끝낸 비율)과 재사용 의향이 올라간다. (목표: 정산 기능 사용률 70% 이상)
- **제품**: 반복 1 결과 반영 개선 + 정산 도우미 추가.
- **측정(KPI)**: 정산 기능 사용률, 팟 완료율, 사용 후 설문(NPS/재사용 의향).

### 반복 3 — 반복 1·2 데이터가 알려주는 것
- **후보 가설 H3-a (신뢰 문제)**: 참여율이 낮다면 → 학교 이메일 인증 추가 시 참여 전환율 상승.
- **후보 가설 H3-b (유동성 문제)**: 팟이 안 모인다면 → 출발 시간을 10분 단위 슬롯으로
  묶어 추천하면 매칭 성사율 상승.
- 실제 데이터를 보고 하나를 선택 — **"데이터가 다음 가설을 결정했다"는 스토리 자체가 발표 핵심.**
- **측정(KPI)**: 선택한 가설에 대응하는 전환율 비교 (before/after).

### 북극성 지표 (전체 KPI)
- **매칭 성사율** (핵심), 매칭 소요 시간, 1인당 절감 택시비(추정), 주간 재방문율.

## 6. 기술 스택 & 개발 순서 (조교님 가이드 그대로)

| 단계 | 도구 | 내용 |
|---|---|---|
| 1 | GitHub | 저장소 생성 (모노레포, Next.js) |
| 2 | Vercel | GitHub 연동 자동 배포 (계정 신규 생성 — GitHub으로 가입) |
| 3 | Supabase | DB(팟, 참여자, 정산), Auth(반복 3에서 이메일 인증 시) — 계정 신규 생성 |
| 4 | GA4 | 페이지뷰 + 커스텀 이벤트(팟 개설, 참여, 정산 사용) |
| 5 | Search Console | 도메인 등록, sitemap 제출 |

프레임워크: **Next.js (App Router) + Supabase JS + Tailwind CSS**. 웹 개발 경험이
있으므로 무리 없는 조합이고, Vercel 배포가 가장 매끄러움.

## 7. 주차별 일정 (4주 기준)

- **1주차**: 문서 확정(문제/페르소나/시나리오/H1) → 셋업(GitHub·Vercel·Supabase·GA4)
  → 반복 1 MVP 개발·배포 → 지인 테스트 시작.
- **2주차**: 반복 1 데이터 수집·분석 → H2 수립 → 정산 기능 개발·배포 → 테스트 2차.
- **3주차**: 반복 2 분석 → H3 선택·개발·배포 → Search Console 등록 → 최종 데이터 수집.
- **4주차**: 결과 정리(반복 3회의 가설-제품-측정 표), 발표 자료 제작, **5분 발표 영상 촬영·편집**, 제출.
